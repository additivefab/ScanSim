# 提示词 — 给用户用

在 `zlscan_v5/` 目录下启动代理（Claude Code 或 Codex）后，把下面对应的一段粘贴过去。两种代理通用。

规则都写在仓库里，所以提示词可以很短。切换代理时不需要转述上下文，让新代理读 PROGRESS.md 即可。

## 1. 第一次开始

```text
请先读 AGENTS.md，再按它第 2 节的顺序读完必读文档。
读完后不要写代码，先告诉我：
1) 你理解的当前状态和下一个任务；
2) DECISIONS.md 里"待用户决定"中哪些会挡住当前阶段，需要我现在回答；
3) 你发现的文档之间的矛盾或不清楚的地方。
```

## 2. 开始或继续一个任务

```text
读 AGENTS.md 和 docs/dev/PROGRESS.md，继续当前阶段的下一个任务。
一次只做一个任务。做完后跑 ruff 和 pytest，提交，更新 PROGRESS.md，然后停下来向我汇报：
实际运行了哪些命令、结果如何、有没有改规格、下一步是什么。
```

指定任务时把第一句换成：`读 AGENTS.md 和 docs/dev/PROGRESS.md，做任务 S0-T03。`

## 3. 连续推进多个任务

```text
读 AGENTS.md 和 docs/dev/PROGRESS.md，从当前任务开始连续推进本阶段的任务。
每完成一个任务就提交并更新 PROGRESS.md，然后继续下一个。
遇到 DECISIONS.md "待用户决定"里的事项、需要安装系统软件、测试对不上基准值、或发现规格有错时，停下来问我。
```

## 4. 切换代理后的接手

```text
你是接手的代理，之前由另一个代理开发。
读 AGENTS.md 和 docs/dev/PROGRESS.md。
先运行 git status、git log --oneline -15 和测试，确认 PROGRESS.md 的记录与仓库实际状态一致。
不一致的地方列给我，不要自行修正历史。一致的话，告诉我你准备从哪个任务继续。
```

## 5. 阶段门槛验收

```text
读 AGENTS.md、docs/dev/PROGRESS.md 和 docs/dev/stages/stageN.md。
对照该阶段的"阶段门槛"逐条核查。每一条都要实际运行对应的测试或命令，不要引用 PROGRESS.md 里的旧结论。
给我一张表：门槛项、你运行的命令、结果（通过 / 失败 / 未执行）、证据在哪里。
有未通过的项不要进入下一阶段。
```

把 `stageN` 换成实际阶段。

## 6. 让另一个代理审查

适合在一个代理完成一个阶段后，换另一个代理来审。

```text
请审查最近的提交（git log 里从 <起点> 到 HEAD）。
读 AGENTS.md 的硬性规则和 docs/dev/07_evidence_rules.md。重点查：
1) 有没有违反硬性规则：真值泄漏、静默夹紧、对数码先平均、按行重置状态、未知值填了默认数；
2) 有没有把没运行的东西写成通过；
3) 测试是否真的在验证它声称验证的东西，有没有为了通过而放宽断言；
4) 规格文档与代码是否一致。
只报告你确认的问题，每条给出文件和行号。不要改代码。
```

## 7. 进入提纲阶段（阶段 5、6、7）之前

```text
读 AGENTS.md、docs/dev/PROGRESS.md 和 docs/dev/stages/stageN.md。
这个阶段的任务说明只是提纲。请先把任务细化成可执行的子任务，
并为需要新物理模型的任务写出 ModuleSpec 和方程草稿。
先不要写代码，把细化结果和规格草稿给我确认。
```

## 8. 我提供了新资料

```text
我提供了新资料：<说明是什么、放在哪里>。
读 AGENTS.md、docs/dev/DECISIONS.md 第三部分和 docs/dev/stages/stage6.md。
告诉我：这份资料对应哪一项（R001–R007 或 M01–M08）、能解锁什么、
哪些参数可以从"假设"升级、哪些还不够。先不要改参数，等我确认。
```

## 9. 回答待决事项

```text
关于 DECISIONS.md 的 Q00x，我的决定是：<……>。
请更新 DECISIONS.md（移到"已定决策"，记入变更日志），并说明这会影响哪些任务。
```

## 使用建议

- 每个阶段结束时用第 5 条做一次验收，最好再换一个代理用第 6 条审一遍。
- 代理说"测试通过"时，可以让它贴出命令和输出的最后几行。
- 两个代理不要同时改同一个仓库。切换前确认上一个代理已提交并更新了 PROGRESS.md。
